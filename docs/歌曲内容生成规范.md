# RED:REPEAT 歌曲内容生成规范 1.1

本文是 `library/<song-id>/` source package、Validator、Compiler、Runtime、播放器和内容校准工作的共同规范。字段以当前公开代码为准；不满足 contract 的内容不能进入可消费的 Runtime。

1.1 的内容生产原则是把首次可用导入与人工精确校准分成两个阶段：

```text
原曲 + LRC + 翻译 + 封面
→ 结构化 intake / 粗 timing
→ Provisional Timing source
→ validate / compile
→ Production 首次交付
→ 用户通过 Production Timing Debugger 实际试听和校准
→ Timing Correction Export
→ focused canonical timing correction
→ Calibrated Timing
```

浏览器里的个人微调是人工 QA 工具，不是 source 编辑器。`Provisional Timing`
是可用的首次导入状态，不是 `human audible PASS`；只有用户实际校准并经
identity 校验、focused merge 的范围，才能记录为 `Calibrated Timing`。

## 1. Source package

正式 source root 是仓库根目录下的 `library/`。每首歌放在一个小写、URL/filesystem-safe 的目录中：

```text
library/
└── <song-id>/
    ├── manifest.json       # required
    ├── lyrics.json         # required
    ├── timeline.json       # required
    ├── practice.json       # required
    ├── audio/
    │   └── source.<input-extension>   # required, exactly one
    ├── artwork/
    │   ├── cover.<input-extension>    # required, exactly one
    │   └── hero.<input-extension>     # optional, at most one
    └── features/
        └── *.md            # optional
```

`<song-id>` 和 `manifest.json.songId` 必须完全一致，并匹配：

```text
^[a-z0-9]+(?:-[a-z0-9]+)*$
```

根目录下以 `.` 开头的目录不会被发现。JSON object 是 strict contract；未定义字段、重复 id、缺少引用目标都应在 Validator 阶段失败。

### 1.1 Structured Song Handoff｜结构化歌曲交接包

新曲任务可以由 Architect/source handoff 以结构化 task package 提供。典型
Handoff 包含：

- 当前 `Plan`、`README-CODEX-INTAKE` 与边界/验收说明；
- exact audio/artwork assets、对应 hash baselines 和 source notes；
- `manifest candidate`；
- canonical Japanese lyrics、translation/ruby candidate 及 translation mapping；
- Segment/Occurrence mapping、Section/Practice candidates 和 `Provisional Timing`
  candidate；
- `features/*.md` 的完整 draft，以及 official/interview/media source synthesis。

Structured Song Handoff 是 task input，不是 `library/<song-id>/` 的 canonical
source。Codex 必须先核验其完整性、hash、audio identity、schema/reference/path
和事实边界，再将明确授权且通过 contract 的部分落入 tracked source。Exact user
assets 应在导入前重新计算 hash 并按原始字节复制；除非 source contract 明确
要求转换，不得 canonical recompress/re-encode。不得把整个 intake ZIP、
provenance 目录或临时研究输出机械提交。Generated runtime conversion 仍由
Compiler 负责。

`public/library-runtime/` 是 Compiler 生成的 Runtime 输出，不是内容编辑目录。不要直接编辑其中的 JSON、音频或图片；修改 source 后重新 validate/compile。`dist/` 同样是构建产物。

如果需要对不同 source root 做本地验证，使用 CLI 的 `--source-root` 或 `RED_REPEAT_LIBRARY_ROOT`；默认工作流仍然是 `library/`。

## 2. `manifest.json`

最小示例：

```json
{
  "songId": "first-light",
  "title": "First Light",
  "artist": "A Composer",
  "album": "Synthetic Sessions",
  "year": 2026,
  "intro": "A short introduction, at most 280 characters."
}
```

字段规则：

| 字段 | 必需 | 规则 |
| --- | --- | --- |
| `songId` | 是 | URL/filesystem-safe slug；必须等于目录名 |
| `title` | 是 | 非空文本 |
| `artist` | 是 | 非空文本 |
| `album` | 否 | 非空文本 |
| `year` | 否 | 非负整数 |
| `intro` | 否 | 非空文本，最多 280 字符 |

`title`、`artist` 是 Library card、歌曲页和导出修复包的公开元数据。不要把内部文件名、临时研究标记或未确认的版本说明写入这些字段。

Artist / metadata authoring：

- 歌曲信息优先取用户提供的文件名、tag、歌词包和明确说明。
- 用户材料与现实资料发生实质冲突时，先停止并请求确认，不擅自“纠正”。
- artist 有成熟、自然的中文名称时优先使用中文；没有成熟中文译名时保留原名。
- 多 artist 的顺序按用户材料体现的主要度与自然顺序处理，不凭模型主观重排。
- 这是 display metadata authoring rule；除非当前 repo 有明确必要，不把
  `artist: string` 扩成复杂的多实体 schema。

## 3. `lyrics.json`：Segment 内容

```json
{
  "segments": [
    {
      "id": "s001",
      "lyrics": "A line worth returning to",
      "ruby": [
        { "start": 0, "end": 1, "base": "歌", "reading": "うた" }
      ],
      "translation": "一行值得反复回到的歌词",
      "layers": [
        { "id": "reading", "label": "Reading", "text": "..." }
      ],
      "notes": [
        { "title": "Optional note", "body": "A high-value note." }
      ],
      "emphasis": "subtle"
    }
  ]
}
```

`Segment` 规则：

- `id` 必须匹配 `^s[0-9]+[A-Za-z0-9_-]*$`，并在文件内唯一。
- `lyrics` 是 canonical 原文，不能为空。保持原有语言、标点和必要的空格。
- `ruby` 可选，用于在 canonical 原文上表达可定位的振假名。每项使用
  JavaScript 字符串的半开区间 `[start, end)`、与该区间完全一致的 `base`
  和平假名 `reading`；`base` 不得脱离 `lyrics` 单独改写。
- 只要 `lyrics` 含有 Han 或 Katakana 字符，每个这样的字符都必须被至少一个
  ruby span 覆盖；span 不得 overlap、越界或互相包含，`reading` 不得为空或含
  Katakana。一个 span 可以覆盖带 okurigana 的词、jukujikun/特殊读法或其他
  有语义的多字符范围，不要求逐字拆分。纯英文歌词不需要 `ruby`。
- `translation` 是当前产品必需的非空文本；没有可靠翻译时应先人工确认，不用占位符掩盖缺失。
  Handoff 中用户明确提供或确认的 translation 具有内容 authority；Japanese
  source/evidence 只用于核对 mapping，不授权 Codex 独立替换该 translation。
- `layers` 可选。每项需要非空 `id`、`label`、`text`，只添加对学唱有帮助的读音、语法或其他层。
- `ruby` 与既有 `layers` 并存；ruby 是原文内联读音 contract，`layers` 仍保持向后兼容，不能为了迁移而删除既有读音或其他学习层。
- `notes` 可选。每项需要非空 `body`，`title` 可选；不要为了填结构强迫每句都有 notes。
- `emphasis` 可选，只能是 `subtle` 或 `strong`。

Segment 不携带真实时间。它是可被多个 Occurrence 重复引用的内容单元；时间和歌曲结构属于 `timeline.json`。

### 3.1 振假名 / Ruby

振假名只标注可由 source 证据确认的读法。输入时先保持 `lyrics` 的原始字形、
标点、大小写和空格，再以位置 span 记录读法：

```json
{
  "lyrics": "名詮自性です",
  "ruby": [
    { "start": 0, "end": 4, "base": "名詮自性", "reading": "みょうせんじしょう" }
  ]
}
```

`reading` 使用平假名；片假名词在 reading 中转换为平假名，必要时可保留日语长音符
`ー`。mixed okurigana、jukujikun 和特殊字形读法可作为一个 semantic span，
但必须通过 `base` 与 canonical lyric 的精确位置校验。Validator 会拒绝 base
不一致、越界、overlap、缺少 Han/Katakana coverage 或非法读法。Compiler 将
该字段原样带入 Runtime；UI 使用语义 `<ruby>/<rt>` 展示，canonical lyric
仍作为复制、无障碍名称和播放/引用语义的原文。

## 4. `timeline.json`：Section 与 Occurrence

```json
{
  "audioSourceHash": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "sections": [
    { "id": "verse-1", "label": "Verse 1", "startMs": 0, "endMs": 12000 },
    { "id": "instrumental", "label": "Instrumental", "startMs": 12000, "endMs": 16000 }
  ],
  "occurrences": [
    {
      "id": "o001",
      "segmentId": "s001",
      "sectionId": "verse-1",
      "startMs": 700,
      "endMs": 3900,
      "performanceNote": "Optional human performance note."
    }
  ]
}
```

### 4.1 音频身份

`audioSourceHash` 是 canonical `audio/source.*` 文件的原始字节 SHA-256。它不是编译后的 M4A hash，也不是 JSON 内容 hash。

```bash
npm run library:audio-hash -- <song-id>
```

替换 source audio 后必须重新计算并更新 `timeline.json.audioSourceHash`，再执行 Validator、Compiler 和人工试听。Validator 会拒绝 hash 不匹配的 Timeline。

### 4.2 Section

Section 表示音乐结构，而不是手机上每一页练习的大小。它可以是 Verse、Chorus、Bridge、Intro、Outro、Rap、Break 或纯器乐段。

- `id` 必须唯一，匹配 `^[a-z][a-z0-9_-]*$`。
- `label` 必须是非空文本。
- `startMs`、`endMs` 是非负整数，并满足 `startMs < endMs`。
- 时间范围使用半开区间 `[startMs, endMs)`；等于 `endMs` 的时刻已经离开该 Section。
- Section 按 source order 声明；时间不得倒退，Section 之间不得 overlap。
- 合法 gap 可以存在，Section 不要求无缝覆盖整首音频。
- 没有歌词 Occurrence 的纯器乐 Section 是合法的；Runtime 会将它渲染为可播放的器乐项。

### 4.3 Occurrence

Occurrence 表示一个 Segment 在真实时间轴上的一次出现。它只有一组权威 timing，
所有字段都是非负整数毫秒：

```text
0 <= startMs < endMs
```

`startMs/endMs` 同时是：

```text
startMs / endMs
= 编辑、歌词高亮、播放和练习使用的唯一实际演唱/transport 范围
```

规则：

- `id` 必须唯一，匹配 `^o[0-9]+[A-Za-z0-9_-]*$`。
- `segmentId` 必须引用 `lyrics.json` 中存在的 Segment。
- `sectionId` 必须引用 `timeline.json` 中存在的 Section。
- `0 <= startMs < endMs`；这是该 Occurrence 的唯一时序约束。
- `startMs/endMs` 可以跨越所属 Section 边界；Section 是音乐结构区间，不是
  Occurrence 的机械裁剪框。当 pickup、尾音、间奏或重叠需要这样做时，不要用
  Section 边界强行截断。
- 不同 Occurrence 的 timing 可以 overlap；不要为了消除真实的叠唱或对位而合并它们。
- `performanceNote` 可选，用于记录真实演唱、叠唱、呼吸或 QA 风险，不要把临时猜测写成确定事实。

## 5. 初始 Timing：Provisional 与 Calibrated 两阶段

本规范会被 intake handoff、GPT 与歌曲素材一起使用来生成导入包。首次导入
不以“全部 Occurrence 已完成人工级毫秒校准”为前置条件，但仍必须达到
`Provisional Timing` 的最低可用边界。后续用户校准形成 `Calibrated Timing`。

### 5.1 Provisional Timing

`Provisional Timing` 用于新歌首次进入 Production，让 Practice、Full Song
和 Timing Debugger 可以直接使用。它的最低要求是：

- canonical audio hash 已验证，且 `timeline.json.audioSourceHash` 与当前
  `audio/source.*` 一致；
- 每个歌词 Occurrence 都有有效的 `startMs/endMs`，满足 `0 <= startMs < endMs`；
- LRC 只作为粗 anchor；允许使用轻量 audio analysis 修正明显偏差；
- 不得明显把上一句或下一句的大段清晰音节带入当前句；
- intro、instrumental、section transition、outro 不得明显错归；
- 不得使用 `end = next LRC timestamp` 或整曲统一 `-N/+M` fixed padding；
- 可以保留几十到几百毫秒级的待用户精调空间；
- source/state 必须清楚记录它尚未经过 human calibration，不得写成 audible
  PASS。

Provisional Timing 的目标是“首次可用且没有明显边界错误”，不是替用户完成
全部逐句听感判断。发现明显 timing ambiguity、neighbor leakage 或 audio
identity conflict 时，必须暂停交付并深入调查；没有这些信号时，不要求为全部
Occurrence 制作完整 waveform/spectrogram evidence。

### 5.2 Calibrated Timing

`Calibrated Timing` 只表示用户通过 Production Timing Debugger 实际试听、
调整并导出后，已由 Codex 将对应 correction focused 合入 canonical source
的范围。它的来源可以是当前 Edition identity 下的 Debugger export、用户明确
提交的 timing correction package，必要时附带用户说明。

合入要求：

- correction 必须匹配 song、Edition、audio 和 Timeline identity；
- Codex 只修改 export 覆盖的 timing 与必要的 matching notes，不顺手重写
  lyrics、Practice、Section、audio 或其他歌曲内容；
- validate / compile / build 后进行 focused commit 与 normal push；
- `CURRENT_STATE.md` 按事实记录已校准的范围；未被用户实际校准的
  Occurrence 不得虚构为 `Calibrated Timing` 或 human PASS。

```text
startMs ≈ 当前句第一个可听音节 / 音符的 onset
endMs   ≈ 当前句最后一个可听音节 / 音符的 offset
```

### 5.3 唯一时间区间的生成顺序

1. 根据音频确定唯一的 `startMs/endMs`，同时作为编辑、歌词高亮和所有播放行为的范围。
2. 不得把候选区间复制后统一减去一个 lead、加上一个 tail 作为默认结果。
3. 不得根据歌词行长度、标点、LRC 行跨度、ASR 的整行时间或前后 Occurrence
   的文字关系，推导出整句外扩的区间。
4. 如果需要保留明显的吸气、pickup、延音释放、混响或教学留白，必须把它作为
   有音频依据的例外，并在 `performanceNote` 中说明。

### 5.4 外扩默认值不是固定 padding

```text
普通句：lead-in 0–80ms，tail 0–100ms
快速 Rap / 日英混合 / 极密歌词：lead-in 0–60ms，tail 0–80ms
超过 120ms 的起点外扩，或超过 160ms 的终点外扩：必须有音频依据和 performanceNote
```

以上是 Provisional 候选的保守参考范围，不是允许 GPT 批量套用的固定值。以下行为明确禁止：

- 对整份歌曲的每句都使用相同的 `startMs = candidateStart - N` 和
  `endMs = candidateEnd + M`。
- 使用 `-280ms / +420ms` 或任何同类的统一整句 padding。
- 为了“保证完整”而把前一句尾音、后一句起音、邻近歌词行或整段空白带进当前句。
- 把一整行歌词的时间跨度当成当前句的可听 onset/offset。
- 看到人工边界比候选范围窄时，擅自向外放宽或在导入时恢复旧的 envelope contract。

### 5.5 相邻句与重叠句的边界

对于不存在真实 overlap 的相邻句，先识别当前句的可听 offset 和下一句的可听 onset，
再留出很小的 guard gap：

```text
candidateEnd = min(currentAudibleOffset + smallTail, nextAudibleOnset - guardMs)
```

`nextOccurrence.startMs` 只能作为待复核的候选参考，不能代替下一句的音频 onset。
guard gap 的目的是防止清晰音节泄漏，不是把前一句强行截短到听起来不完整。
如果存在真实 overlap、连唱、延音、叠唱或对位，不要用 guard gap 消除它们：
保留各自 Occurrence，在 `performanceNote` 中说明 primary 顺序和边界风险。

### 5.6 生成后的必做检查

每次 GPT 批量生成后，必须优先复核：

- 第一条歌词的真实起音，而不是把歌曲开头空白或前奏当成 lead-in。
- 快速 Rap、日英混合、密集辅音和相邻无停顿句，确认前后句没有互相带入音节。
- 每个 Section 的最后一句、间奏边界和重启点。
- 02:40 之后等叠唱、对位、持续音和真实 overlap 段，确认没有用单句窗口覆盖多条声部。
- 最后一句的释放点、拖尾和空白，确认没有把整段尾部静音留给当前句。
- 重复副歌和相同 Segment 的每次 Occurrence，确认都对应正确的音频位置。

批量结果出现以下信号时，必须停止继续自动放宽并转人工听取：

- 大量句子的 lead-in 或 tail 数值完全相同。
- 多数句子的 `startMs` 明显早于第一个可听音节，或 `endMs` 明显晚于最后一个可听音节。
- 相邻 Occurrence 的 timing 区间把前后句清晰音节同时包含进来。
- 唯一 timing 被统一扩大，却没有音频证据支持。

这只是 `Provisional Timing`，不是最终 `Calibrated Timing`。真实 overlap、连唱和
持续音在用户校准时需要人工试听确认；不能为了满足 guard gap 强行截断仍然在
发声的当前词。Validator 可以对异常宽的 lead/tail 发出 non-blocking QA warning，
但不得把合法的窄 timing 或真实 overlap 变成硬错误。

### 5.7 角色分工与两阶段交接

#### Architect / source handoff

Architect/source handoff 负责上游内容包的研究、统合和候选产物：

- 歌曲背景及 official/interview/media source synthesis；
- Explain 主题设计、资料边界和 `features/*.md` 完整正文草稿；
- audio identity、metadata/manifest candidate、LRC parsing 和 translation mapping；
- canonical Japanese lyrics、translation/ruby candidate、unique Segment mapping
  和 Occurrence mapping；
- Section candidate、Practice Unit candidate、Provisional Timing candidate 及
  intro / interlude / outro 的 coarse topology；
- 用户提供的 exact artwork/audio packaging、hash baselines 和 source notes。

`README-CODEX-INTAKE` 应标明内容或资产属于 exact、candidate 还是 editorial，
并记录已知不确定项。对已结构化提供的、已获批准的 content、mapping 或 exact
asset，Codex 不应无冲突地重复研究、翻译润色、文章重写或结构推导；这不改变
Handoff 只是 task input 的性质。

#### Codex

Codex 负责 repo inspection、可执行 contract validation、将选定内容集成进
`library/<song-id>/`、必要的 contract/path/reference/format 修复，以及
validate / compile / build、相关 regression 和获授权的 release/push/deploy。
Codex 也负责报告 Handoff、当前 repo contract 和可靠事实之间的实质冲突。

Codex 不应独立重写已批准的歌词、translation、ruby、Explain 正文、metadata、
Segment/Occurrence mapping、Section/Practice candidate 或 exact asset，也不应
为了证明“精确”重复整轮内容研究或制作大量临时 DSP artifact。若必须进行
Explain 的语义性改写，必须作为 Plan deviation 报告；若发生 schema/reference、
hash/audio identity、collision 或可靠事实冲突，不得静默改写用户材料，应停下
并请求用户/Architect 决定。对 Provisional Timing，除非发现 timing ambiguity、
neighbor leakage 或 audio identity conflict，否则不重复 full forensic analysis。

#### User

用户主责最终的主观 timing refinement：在手机或真实使用环境打开 Timing
Debugger，试听，调整 correction package 所覆盖的唯一字段 `startMs/endMs`，
导出 `Timing Correction Export`，有问题时反馈。用户的本机 override 不等于已经
合入 canonical source；Codex 必须在 identity 校验后做 focused correction。

## 6. `practice.json`：Practice Unit

Section 描述音乐结构，Practice Unit 描述教学练习段。两者不要混用：不要为了让歌曲地图短小而把音乐 Section 切得过碎。

```json
{
  "units": [
    {
      "id": "p001",
      "sectionId": "verse-1",
      "label": "主歌 A",
      "occurrenceIds": ["o001", "o002", "o003"]
    }
  ]
}
```

规则：

- `practice.json` 必需；每个 Unit 的 `id` 必须唯一并匹配 `^p[0-9]+[A-Za-z0-9_-]*$`。
- `label` 必须非空，`occurrenceIds` 必须非空。
- 每个 Occurrence 必须恰好被一个 Practice Unit 覆盖一次。
- `sectionId` 必须引用现有 Section；Unit 内所有 Occurrence 必须属于同一 Section。
- Unit 内 Occurrence 按实际时间递增，Units 按第一条 Occurrence 的时间递增。
- 纯器乐 Section 没有歌词 Occurrence，因此不需要 Unit。
- 3–6 个 Occurrence、约 10–30 秒是 editorial guidance，不是硬性时长规则。
- 不加入 `difficulty`、`mastery`、`recommendedRepeats` 或学习统计字段；这些不是 content contract。
- 当已有歌曲需要重组练习段时，优先保留原有 Occurrence ID、Section 和 timing；
  Practice Unit 的边界可以按旋律连续、呼吸/停顿、编曲转折、语义推进和自然连续
  播放重新确定。旧本机 resume 的 Unit ID 不应被当作新边界的唯一身份，Runtime
  应优先用稳定的 Occurrence ID 重新归属，避免旧 ID 映射到错误的练习段。

当前产品的 Practice UI 只围绕 Practice Unit 提供单句、连续播放、渐速和三个固定速度。不要把旧的训练策略、循环次数、范围编辑或播放切口编辑重新写进 `practice.json`。

## 7. Feature Markdown：讲解内容

`features/*.md` 是可选的讲解内容。每个 Feature descriptor 的 `id` 和 URL 由 Compiler 生成，文章正文由内容作者维护。文章应以一个一级标题开始，并可以使用：

```markdown
# 主题标题

与歌曲直接相关的正文。

[[segment:s001]]
```

歌词引用使用 `[[segment:<segment-id>]]`。它会在讲解页面原地显示带 ruby 的原文、翻译、可用 reading layer 和试听/学唱入口；不要在文章里复制一份带时间的歌词。

Feature 可以写：

- 歌词含义、语言表达、双关、典故；
- 曲式、编曲、节奏、唱法和制作细节；
- 创作、专辑、艺术家、合作、动画/电影/游戏关联和发行背景；
- 采访趣事、制作花絮、名场面、社区常见解读；
- 与歌词直接相关的乐器、音乐风格、文化、历史或科学知识。

来源要求可以按内容类型选择官方资料、艺术家采访、制作方资料、可信媒体、百科、社区讨论或视频考据，但必须区分：

`features/*.md` 默认由 Architect/source handoff 完成资料研究、Explain 主题
设计和完整正文。Codex 默认只校验 Markdown、路径、编译、Segment 引用和必要的
contract/format；不得在没有冲突时重新搜索资料或重写文章。正文中的事实边界应
分别标记：

```text
confirmed fact
creator statement
media analysis
common interpretation
RED:REPEAT editorial observation
```

不要把猜测写成确定事实；不要为了“完整”写成与歌曲无关的长论文。Feature 的目标是有关系、值得点开、能帮助用户继续听和学唱。

## 8. Media 与 Runtime 输出

### 8.1 Audio

- canonical audio 是 `audio/source.*`，必须只有一个匹配文件。
- Compiler 将 source 转为 Runtime 可播放的 M4A；当前 contract 要求 AAC-LC、192 Kbps、双声道，采样率为 44100 或 48000。
- 替换 source 后必须重新计算 hash，并重新校准所有依赖音频身份的 Timeline。

### 8.2 Artwork

- `artwork/cover.*` 必需且只能一个；`artwork/hero.*` 可选且只能一个。
- Compiler 生成 small/large WebP Runtime asset。
- 图片只承担歌曲识别和产品展示，不加入额外的运行时视觉语义字段。

### 8.3 Runtime contract

当前 Runtime contract version 为 `3`。每个 Edition 至少包含：

```text
contractVersion
contentHash
song
lyricsUrl
timelineUrl
practiceUrl
features
audio
artwork
```

`edition.contentHash` 代表这份 Song Edition 的内容身份。浏览器本机保存的 Timing 微调只在相同 Edition hash、相同 audio source hash 和相同 Timeline identity 下有效；新 Edition 载入时旧记录会自动清理。

## 9. Validator / Compiler 工作流

日常 source 修改后，按顺序执行：

```bash
npm run library:validate
npm run library:compile
npm run build
npm run pwa:inspect
```

只修改 timing 时仍然要运行完整 Validator，因为它会检查：

- source package 与目录名一致；
- JSON schema 和严格字段；
- id 引用、重复和覆盖关系；
- Section 与 Occurrence 时间关系；
- Practice Unit 顺序和覆盖；
- audioSourceHash 与实际 canonical audio 一致。

Compiler 会生成 `public/library-runtime/`，并为 catalog、Edition、歌词、Timeline、Practice、Feature、媒体和 artwork 生成带 hash 的 Runtime asset。不要手工编辑生成文件来“修复”内容。

如果要确认发布路径，额外执行：

```bash
npm run build -- --base=/red-repeat/
npm run pwa:inspect -- /red-repeat/
```

## 10. 播放切口调试与 Codex 修复闭环

正常产品入口是：

```text
设置 → 播放切口调试 → 选择歌曲
```

普通歌曲页只保留：

```text
学唱 | 全曲 | 讲解
```

Production Timing Debugger 是逐句人工 QA 与后续校准工具，显示完整歌词流和当前句控制台。当前公开页面只调整：

- `startMs`；
- `endMs`；
- `-100 / -20 / +20 / +100ms`；
- 将当前播放位置设为起点或终点；
- 试听当前句；
- 上一句、下一句、恢复当前句默认。

它只编辑 Occurrence 的唯一 `startMs/endMs`，不编辑 Section 或歌词内容，也不把
Provisional Timing 描述为最终 timing。

本规范所称 `Timing Correction Export`，指通过 `设置 → 微调导出` 生成的
Markdown 修复包，而不是浏览器直接写入 Git。当前 Production Timing Debugger
及其 Settings export 的实际可导字段是 `startMs` / `endMs`；它们用于
identity-bound 的唯一 timing 校准，同时控制歌词解析和 bounded playback。

调试器保存的是本机 Timing Override。歌曲核心层将：

```text
canonical timeline
+ compatible local override
→ one Effective Timing provider
```

再传给所有 bounded occurrence playback consumer：

- Practice 单句和连续范围首尾；
- Full Song 从歌词开始连续播放和“再听这句”；
- Explain 歌词引用试听；
- 其他未来的 occurrence bounded playback。

调试后进入：

```text
设置 → 微调导出
```

导出文件是：

```text
red-repeat-timing-fix-<song-id>.md
red-repeat-timing-fixes-all.md
```

修复包必须包含：

- repo、target source、song title/artist/songId；
- app version、build SHA；
- Edition content hash、audio source hash、Timeline runtime identity；
- 每个改动 Occurrence 的原文、Section、canonical `startMs/endMs`、override 值和 delta；
- 稳定 JSON machine-readable block；
- 只修改列出 Occurrence 的 Codex prompt；当前公开 export 覆盖的字段以
  `startMs` / `endMs` 为准，不得把未导出的字段当作用户已校准。

当前 export contract 已足够安全地进入 canonical correction：它包含
`songId`、`Edition content hash`、`audio source hash`、canonical Timeline
runtime identity（`baseTimelineUrl`）、target source、build identity、逐条
Occurrence 的 canonical/override/delta，以及稳定 JSON machine-readable block。
应用前仍必须把这些字段与当前 source/runtime 逐项比对；identity mismatch、
不存在的 Occurrence 或 invalid timing 都必须拒绝，不能靠人工猜测覆盖。

首次导入闭环：

```text
结构化 intake
→ Provisional Timing source
→ validate / compile / build
→ Production 首次交付
```

校准闭环：

```text
真实试听
→ Production Timing Debugger
→ identity-bound 本机微调
→ 设置 / 微调导出
→ Codex 校验 identity 并只修改 export 覆盖的 timing
→ validate / compile / test / build / pwa:inspect
→ focused commit / normal push
→ 覆盖范围记录为 Calibrated Timing
→ 新 Edition content hash
→ 客户端自动清除旧本机微调
```

浏览器不直接写 Git，不存 GitHub token，不执行 commit，也不把本机 override
当成已经合入 source 的事实。若没有用户实际试听和 correction export，仍只能
记录为 Provisional Timing；没有被实际校准的 Occurrence 不得写成 human PASS。

## 11. Timing QA 两阶段清单

### 11.1 Provisional Timing 最低检查

首次导入不要求对每个 Occurrence 完成人工级逐句听取，但必须完成以下粗检：

1. canonical audio hash 已计算并与 `timeline.json.audioSourceHash` 一致。
2. 所有 Occurrence 的 `startMs/endMs` 都有效，LRC anchor 与 occurrence/order
   没有严重错位。
3. 第一条歌词没有把长 intro 包进当前句，最后一句没有把整段 outro 尾奏占用。
4. Section end、instrumental、break、重启点没有明显错归给歌词 Occurrence。
5. 相邻句没有大段清晰音节串音；long gap 没有被任意一条歌词占用。
6. 重复副歌和相同 Segment 的每次 Occurrence 都对应正确的粗略音频位置。

上述检查可以使用 LRC、轻量 audio analysis 和结构性验证；它们不能被描述为
human audible PASS。发现明显 ambiguity、neighbor leakage 或 audio identity
conflict 时，必须停止并转入深入音频调查或用户校准。

### 11.2 Calibrated Timing 人工听感检查

用户实际校准某个范围时，至少检查：

1. 第一条歌词的进入偏移：是否过早、漏掉 lead-in，或晚到吞掉开头音节。
2. 快速日英混合、Rap、密集辅音和相邻无停顿句：上一句是否带入下一句。
3. 每个 Section 的最后一句：`endMs` 是否需要更保守的尾部。
4. Intro、Break、间奏、纯器乐和重启点：Section 切点是否与音乐而不是歌词数量一致。
5. 叠唱、对位和真实 overlap：多个 Occurrence 是否都保留，当前句高亮是否仍有可理解的 primary 顺序。
6. 最后一句拖尾：是否过早截断，或把过长的空白留给播放范围。
7. 重复副歌和相同 Segment 的多个 Occurrence：每次出现是否都对应正确的音频位置。

听取后必须导出 identity-bound correction package。没有逐项听取的范围不得
写成 `Calibrated Timing` 或 human PASS；自动工具只负责提出初值，不能为了
满足“完整”而对整份 `timeline.json` 做大规模自动重写。

## 12. 内容提交前检查

```text
[ ] songId、目录名和 manifest 一致
[ ] lyrics 每个 Segment 有可靠翻译，引用没有悬空
[ ] timeline audioSourceHash 已由当前 source audio 计算
[ ] Section 体现音乐结构，而不是机械按歌词数量切碎
[ ] Practice Unit 覆盖所有歌词 Occurrence 且不跨 Section
[ ] 每个 Occurrence 的 startMs/endMs 满足 0 <= startMs < endMs
[ ] 唯一 timing 没有被固定整句 padding 批量扩大
[ ] Provisional：相邻句尾没有明显清晰音节泄漏；Calibrated：只有实际试听并导出的范围才记录为校准完成
[ ] 快速 Rap / 日英混合段没有把前后句音节带入当前句
[ ] 超过 120ms 起点外扩或 160ms 终点外扩的句子都有明确 QA 说明
[ ] 纯器乐 Section 有明确边界
[ ] Feature 引用使用现有 Segment id，事实与解读分开
[ ] Provisional / Calibrated 状态按实际覆盖范围记录，没有把 provisional 写成 human audible PASS
[ ] Timing Correction Export 的 song / Edition / audio / Timeline identity 与当前 source 匹配
[ ] validate / compile / build / pwa:inspect 通过
[ ] 生成 Runtime 文件未被手工修改
```

内容包完成后，提交 source 变更和必要的公开代码/测试；不要提交由 Compiler 或 Vite 生成的临时产物，除非仓库的发布流程明确要求它们。

## 13. 新曲导入 Plan 默认边界

未来“导入新曲”的 Plan 默认采用以下 acceptance：

- 首次导入以 `Provisional Timing` 为目标；普通逐句毫秒精调不是首次发布 blocker。
- audio hash、gross musical structure、Occurrence/order 和 obvious leakage
  仍是首次导入的 blocker；Provisional 不等于“可以随便按 LRC 切句”。
- 匹配的 automated/local verification 通过后，普通 USER CHECK 默认属于
  `POST-DEPLOY OBSERVATION`；只有当前 Plan 明确要求或属于 D-016 / D-019
  定义的高风险情形，才是 `BLOCKING USER CHECK`。
- 用户导出 `Timing Correction Export` 后，另开 focused timing correction
  Task；Codex 只合入 export 覆盖且通过 identity 校验的字段。
- 不要求 Codex 为每首新歌重复制作全曲 timing forensic report，除非用户
  明确要求，或粗检发现 timing ambiguity、neighbor leakage 或 audio identity
  conflict。
