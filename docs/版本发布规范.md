# RED:REPEAT 版本发布规范

本文规定 RED:REPEAT 如何从真实 Git commit 产生用户版本。版本不与 Plan 编号绑定，也不与 push 次数绑定。

当前 `.github/workflows/ci.yml` 是唯一工作流。推送到 `main` 会先运行
`quality`，成功后由同一工作流中的依赖 `deploy` job 检出相同的
`${{ github.sha }}`、构建 `/red-repeat/` Pages 产物并执行线上身份探针。因此
每次成功的 `main` push 都可能是部署边界；用户版本的批量记录不能被描述成
“main 不部署”。

## 版本级别

所有 focused commit 都要先做一次版本判断：

| 级别 | 语义 | 示例 |
| --- | --- | --- |
| PATCH | 用户可感知、但不改变主要使用方式的小修复或细节调整 | `1.0.0 → 1.0.1` |
| MINOR | 新增能力、重要交互改变或独立产品阶段 | `1.0.1 → 1.1.0` |
| MAJOR | 产品定位、核心训练模型、信息架构或兼容契约发生正式的大幅变化 | `0.9.4 → 1.0.0` |

纯测试、纯文档、格式化、内部重构和不改变运行结果的 tooling 提交可以判定为“不生成用户版本”。这种判断要在交付记录中说明，不能因为 commit 存在就机械增加日志条目。

使用严格的三段式 SemVer：`MAJOR.MINOR.PATCH`。数据层、系统信息、Git tag 和导出内容使用完整版本；界面标题在适合时可以把 `1.1.0` 显示为 `1.1`。

## Ledger 与 commit

唯一版本数据源是 `src/release/releases.ts`。每个用户版本必须包含：

```text
version / date / commit / level / title / summary / changes[]
```

Ledger 按真实发布时间从新到旧排列。`commit` 指向产生用户变化的 focused commit，`date` 必须与该 commit 的提交日期一致。`npm run release:verify` 会检查 SemVer 唯一性、顺序、日期、commit 存在性和当前 package 版本。

commit SHA 只有 commit 完成后才能确定，因此推荐工作流是：

1. 检查实际 diff，判断 PATCH / MINOR / MAJOR 或无用户版本。
2. 创建 focused 产品 commit。
3. 把该 commit 的短 SHA、产品语言的摘要和 changes 写入 ledger；同步更新 package 版本（如果这是最新用户版本）。
4. 创建必要的 ledger 元数据 commit。这个机械性提交不另外产生用户版本。
5. 为第 2 步的产品 commit 创建 `v<semver>` tag。

这样 tag 指向真正改变产品行为的 commit，ledger 也保留可追溯的 commit 节点，不需要自引用 commit hash。

## Tag 与 Plan push

用户版本 tag 的格式固定为：

```text
v1.0.0
v1.1.0
v1.1.1
```

tag 必须唯一、单调，不重用旧版本号，不 force push。一个 Plan 可以产生多个版本，也可以没有新用户版本。Plan/Phase 的分组不改变上述 `main` 部署语义。若要在一个用户版本中批量组织多个变更，应在授权的交付边界统一安排推送；不能在已经推送到 `main` 后再把该推送描述为尚未部署。

普通 no-version 文档/内部维护任务按当前 Task 与 `AGENTS.md` 的明确交付权限提交和推送，不创建 release entry 或 tag。Formal Plan 的 COMPLETE/commit/push 默认只在 Plan 范围完成、匹配验证通过且没有 Stop Condition 或未完成 `BLOCKING USER CHECK` 时适用；`no push`、未归属工作树变更、远端分歧或其他保护条件仍优先。推送当前分支的有效示例为：

```bash
git push origin HEAD
```

这会将当前 checkout 的分支推送到 `origin` 的同名分支。若目标是 `main`，成功 push 会触发前述 CI quality → Pages deploy；Push、CI 和 Deploy 必须分别确认并报告。

只有在用户版本发布已获授权、ledger/package/build identity 已对齐，且本地 tag 指向该版本的用户可见实现 commit 后，才推送指定 tag，例如：

```bash
git push origin v1.2.3
```

本仓库的 `release:verify` 默认检查 ledger 的 SemVer/顺序/日期/commit 与 package 版本关系；它不要求校验所有 Git tag。只有版本/tag 完整性验收适用时，才额外使用 `--require-tags` 检查 ledger tags 的存在、指向及仓库中无孤立版本 tag：

```bash
npm run release:verify
npm run release:verify -- --require-tags
```

如果目标 tag 已存在但指向不同 commit，必须停止并报告，不能覆盖或强制更新。

## Release entry 写作

更新日志面向用户，不直接复制 Git commit message。`title`、`summary` 和 `changes` 使用产品语言，说明用户能获得什么变化；测试 fixture、内部脚本和机械性重构不应出现在更新日志。

更新日志把每个 `x.y.0` 版本视为里程碑。里程碑组不是 SemVer 前缀分组：在下一个里程碑出现之前，后续 PATCH 是 pending；下一个 MINOR 或 MAJOR 里程碑产生后，这些 PATCH 自动归入该新里程碑的 children。
